# Incremental thumbnail workflow

The existing Site is authored in `dist/`. This tooling does not change UI code or run in visitors' browsers. No GitHub repository is involved. Install the pinned tooling with `npm install` inside `tools/`, then `npx playwright install chromium`. The desktop runtime may instead provide `PRISM_TOOL_MODULES` and `PRISM_BROWSER` environment variables. Dependencies are tooling only.

1. After importing updated data, run `node tools/thumbnail-workflow.mjs sync` to restore omitted thumbnail fields for existing resources only when the stable key, exact source URL and stored asset hash match. Then run `node tools/thumbnail-workflow.mjs audit`. Inspect `tools/reports/review.csv` or `review.json`: Keep, Regenerate, Manual Review, Missing. The report also lists identical rasters and orphaned files. It never deletes files. Pixel heuristics identify nearly uniform/blank, low resolution and extreme-aspect images. Legacy screenshots are flagged for content review because pixel metrics alone cannot reliably detect CAPTCHA, cookie banners, relevance or bad crops.
2. Run `node tools/thumbnail-workflow.mjs generate --limit=40`. Only unlocked Regenerate/Missing entries with valid original URLs are eligible. Candidates are staged in `tools/reports/candidates/`, not installed. It tries social previews, meaningful main/article images and identified publication covers, then a cleaned main-content screenshot. Live HTTP status, page text, image dimensions, decode and pixel metrics are checked. It refuses security/login/error pages, does not bypass access controls, and rejects screenshots with remaining cookie/dialog overlays. The original fallback remains if no suitable candidate is found; no fallback replaces an existing raster.
3. Visually inspect the candidate sheets and individual images. Reject logos, unrelated pictures, cookie banners, loading screens and poor crops. Create `tools/reports/approvals.json` containing only reviewed `{ "key": "id:123", "sha256": "exact candidate hash" }` entries from `candidates.json`.
4. Run `node tools/thumbnail-workflow.mjs apply`. This requires exact approved image hashes and checks source URL, original path/hash and lock status again. Assets have stable key+URL filenames, not row-index filenames. It never overwrites a different file. Only thumbnail path/alt fields change in `dist/data.js`; other resource fields and links remain intact. Run audit again after applying.

The registry uses unique original IDs, with source URL verification. Rows lacking a unique ID use a link/title fingerprint. Data reordering does not alter identities. For future updates, retain resource IDs and the thumbnail fields of existing records. A changed URL for an existing ID or a thumbnail changed outside the registry requires explicit reconciliation, not silent reassignment. New resources lacking thumbnails are Missing and eligible. Duplicate/missing IDs with changed titles cannot be matched confidently; assign durable IDs rather than guessing. Two pre-existing empty rows share a fingerprint and remain Manual Review, never eligible for generation. Direct PDF first-page rendering uses Poppler `pdftoppm` (or `PRISM_PDFTOPPM`); the cover is staged for visual review, never cropped to fill. Only tool-owned temporary PDF files are removed after rendering; thumbnail orphans are never deleted.

`thumbnail-registry.json` stores provenance, source, original path/hash and locks. The confirmed UNEP image is `manual`. Because the historic pipeline did not record other manual edits, **all pre-existing non-fallback assets are conservatively locked** as `legacy-unverified`; do not unlock them without human confirmation. After updating a resource to a manually curated local image, run `node tools/thumbnail-workflow.mjs protect --key=id:123` using its exact stable key. This records the current image's hash/path/alt, status `manual`, and locked `true`. Automatic apply cannot override it. Keep registry alongside future dataset updates. The legacy batch refiners are disabled to avoid bypassing locks. The historic one-time review helper is also disabled; never automatically approve future images using old resource IDs.

The full pre-change report is retained as `baseline-review.json`/`.csv`; `review.json` is the current audit. Semantic relevance cannot be certified by pixel statistics: visual approval is mandatory. Direct PDFs or inaccessible sources may need human-supplied official covers; no access-denied screenshot is accepted. No OCR-based classification is claimed for historic screenshot files. The report's Manual Review status explicitly surfaces this uncertainty.
